进入架构设计讨论模式。聚焦于技术方案设计，相比 `/需求讨论` 更加偏向技术实现层面。

**重要：设计模式只讨论不实现。** 可以画出架构图、定义接口、设计数据模型，但不写具体实现代码。

**输入**: `/架构设计` 后面可以是要讨论的主题:
- 模块拆分: "评论系统怎么拆模块"
- 技术选型: "缓存方案 Redis vs 内存"
- 接口设计: "前端 API 层怎么封装"
- 数据模型: "用户权限模型设计"

---

## 讨论方向

按用户话题自然展开，以下为常见方向:

### 模块架构
- 模块边界和职责划分
- 依赖关系和模块通信方式
- 目录结构设计

### 技术选型
- 方案对比（优缺点表格）
- 与现有技术栈的兼容性
- 团队维护成本评估

### 接口设计
- REST API 路径和方法定义
- 请求/响应格式
- 错误码规范

### 数据模型
- Schema 设计（MongoDB/Mongoose）
- 索引策略
- 数据迁移方案

## 工具使用

- 用 **ASCII 图表** 展示架构和数据流
- 用 **Read / Grep** 查看现有模块的实现
- 设计方案写入 `design.md`（属于 OpenSpec 制品）

## 输出示例

```
## 架构讨论: 评论系统模块拆分

### 当前结构
packages/wuh.site.nest/src/modules/comment/
├── comment.module.ts
├── comment.controller.ts  ← 太臃肿，包含业务逻辑
├── comment.service.ts
└── ...

### 建议方案

comment/
├── comment.module.ts
├── comment.controller.ts   ← 只做路由和参数校验
├── comment.service.ts      ← 核心业务逻辑
├── comment.repository.ts   ← 数据访问层（新增）
├── dto/
│   └── comment.dto.ts
└── schemas/
    └── comment.schema.ts

优势:
- controller 变薄，service 可单独测试
- repository 封装 Mongoose 查询，便于切换数据库
- 符合 NestJS 最佳实践
```
